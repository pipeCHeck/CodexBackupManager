## 1. 배경 (관리 대화방이 확인한 사실)
- CLAUDE.md §17 "사용자는 최근 Import 이전 상태로 돌아갈 수 있어야 한다"가 아직 없다. 지금 Snapshot은 "중간에 실패한 Apply 복구"에만 쓴다.
- Snapshot 사본을 통째로 되돌리면 안 된다. 그 Apply 이후 Codex가 쓴 다른 내용이 사라진다. **그 Apply가 쓴 것만 역으로** 처리한다.
- 지금 Apply가 쓰는 것(9_5·9_5a·9_3 이후)
  - rollout 파일: 새 파일(CreateNewFile), 이어 붙이기(AppendToFile)
  - state DB
    - `threads`: INSERT, rollout_path·메타데이터 UPDATE, 연결 변경 UPDATE(project_id·cwd)
    - `projects`·`project_roots`·`project_idempotency_keys`: INSERT
  - global-state: `local-projects` 항목 추가, `project-order` 끝에 추가, 레거시→DB 매핑 추가(새 프로젝트일 때)
  - 따로: SidebarRepairService가 global-state에 같은 세 곳을 추가한다(보정)
- Codex Desktop이 이 PC 데이터를 바꾸는 방식(실측)
  - Desktop을 켜기만 해도(대화를 열지 않아도) 가져온 `threads` 행의 `updated_at_ms`를 바꾸고, `cwd`·`rollout_path`를 `\\?\` 형식으로 바꾼다. `project_id`는 유지한다.
  - 대화를 **열면** `thread_history_1.sqlite`의 `thread_turns`·`thread_items`·`thread_history_projection_state`(`thread_id` 컬럼)에 행이 생기고, global-state `electron-persisted-atom-state`에 thread ID가 언급된다. `session_index.jsonl`에는 줄이 추가되지 않았다.
  - 대화를 **이어 쓰면** rollout 파일이 길어진다.
  - 사용자가 Desktop에서 프로젝트에 대화를 넣으면 global-state `thread-project-assignments`에 기록된다(DB `project_id`가 아님). 고정하면 `pinned-project-ids`에 들어간다.
- 따라서 행 fingerprint에 `updated_at_ms`를 넣지 않는다. `cwd`·`rollout_path`는 원문이 아니라 canonical 경로로 비교한다.
  "Codex에서 열어 본 대화" 판정은 rollout 바이트 변화, thread_history 행, `electron-persisted-atom-state` 언급으로 한다.
- 이 PC의 실제 Snapshot 폴더에는 실제 가져오기 기록(9_0-A, 9_0-B)과 보정 기록(9_0-C)이 들어 있다. 모두 9_4 이전 형식이라 되돌리기 불가로 보여야 한다.

### 9_4-01 Apply 직후 기록(journal 확장)
- 성공한 Apply가 Completed를 기록할 때, 그 Apply가 쓴 것을 **역연산 항목 목록**으로 기록한다. 종류별로 다음을 담는다.
  - 새 rollout 파일: 경로, 길이, SHA-256
  - 이어 붙인 rollout: 경로, 이전 길이·해시, 이후 길이·해시
  - INSERT한 threads 행: thread id, 행 fingerprint
    - fingerprint는 Desktop이 켜지기만 해도 바꾸는 컬럼을 뺀 값의 해시다. `updated_at_ms`는 빼고, cwd·rollout_path는 canonical로 넣는다.
    - 넣은 컬럼 목록을 보고한다.
  - UPDATE한 threads 컬럼: thread id, 컬럼별 이전 값(Snapshot DB 사본에서 읽음)과 이후 값 fingerprint
  - 연결 변경: thread id, 이전 project_id·cwd, 이후 project_id·cwd
  - 새 프로젝트: DB id, name, 루트, idempotency key
  - global-state 추가분: 레거시 id, DB id, 추가한 항목의 name·rootPaths·createdAt
- Summary: 백업 파일 이름, 적용 시각, 개수(새로 가져옴/이어받음/옮김/새 프로젝트), 대상 thread ID 목록. **대화 제목·경로 원문은 넣지 않는다**(경로는 해시나 Snapshot 안의 별도 파일에만). 저장 위치와 방식을 보고한다.
- 기존 journal 호환
  - 새 필드는 선택 필드다. Phase 8 구조 검증(TryReadDetailed)을 약하게 만들지 않는다.
  - 새 필드가 없는 옛 journal은 "되돌리기 불가"로 읽힌다.
  - 쓰기는 기존과 같은 원자적 패턴(temp+flush+move)이다.

### 9_4-02 가져오기 기록 화면

  - 표시: 날짜·시각, 백업 이름, 종류(가져오기/사이드바 보정), 결과, 개수, 되돌리기 가능 여부와 사유
  - 이 PC Snapshot 폴더에는 테스트가 남긴 다른 Home의 Snapshot이 많다. 다른 Home 기록은 넣지 않는다.
- 항목을 고르면 대상 대화(현재 카탈로그의 제목)와 새 프로젝트 목록, [되돌리기] 버튼을 보여 준다.
- 목록을 만드는 동안 Codex Home과 Snapshot 폴더에 쓰기 0건이다.

### 9_4-03 되돌리기(ImportUndoService, Restore 계층)
- 순서는 CLAUDE.md §2.2를 따른다.
  1. 프로세스 락
  2. Codex 실행 확인(시작 + 첫 쓰기 직전)
  3. 같은 Home이고 역연산 목록이 있는지 확인
  4. **전제 조건(항목별)**: 하나라도 맞지 않으면 쓰기 0건으로 거부하고 사유를 준다.
  5. 되돌리기 전용 **새 Snapshot**(되돌리기가 바꿀 파일 전부: 해당 rollout, state DB(+WAL/SHM), global-state)
  6. journal 진행 상태
  7. 역연산
  8. 사후 검증
  9. Undone 기록
- 항목별 전제 조건과 역연산
  - **새로 가져온 대화**: 행 fingerprint 일치, rollout 길이·해시 일치, Codex 흔적 없음(9_4-06) → 행 DELETE, 파일 삭제
  - **이어 붙인 대화**: 이후 길이·해시 일치, 흔적 없음 → 이전 길이로 자르기(앞부분 해시가 이전 해시와 같을 때만, temp+atomic replace), UPDATE 컬럼 이전 값 복원
  - **연결 변경**: 현재 project_id가 이후 값과 같고 cwd가 canonical로 같음 → 이전 project_id·cwd 복원
    - Desktop이 그 대화를 열었어도 rollout을 바꾸지 않았으므로 되돌릴 수 있다. 흔적 검사 대상이 아니다.
  - **새 프로젝트**: 다음 조건이면 프로젝트를 삭제한다(projects·project_roots·project_idempotency_keys 행, 공식 FK 순서에 맞게).
    - 이 되돌리기 후 그 프로젝트를 가리키는 thread가 DB에 없다.
    - global-state에서 그 레거시 id로 가는 `thread-project-assignments`가 없다.
    - `pinned-project-ids`에 없다.
    - 루트·이름이 기록과 같다.
    - 하나라도 아니면 **프로젝트는 남겨 두고** 그렇게 표시한다("Codex에서 이 프로젝트를 사용 중이라 프로젝트는 남겨 두었습니다"). 대화 쪽 되돌리기는 계속한다.
  - **global-state 추가분**(프로젝트를 지울 때만): 9_5a 게이트를 통과한 경우, 추가했던 local-projects 항목(name·rootPaths·createdAt 일치)·project-order 원소·매핑을 제거한다.
    - 같은 직렬화기(GlobalStateJson)로 다른 키는 바이트 그대로 둔다.
    - 항목이 바뀌었거나 게이트에 실패하면 프로젝트를 남긴다(위와 같은 문구).
- DB 작업은 한 트랜잭션이다. global-state는 DB 커밋 뒤에 쓴다(9_5a와 같은 순서). 사후 검증 실패나 도중 실패 → 되돌리기 Snapshot으로 Rollback한다. 문구는 "되돌리기를 취소하고 원래대로 두었습니다"다.
- 한 기록 안에서 되돌릴 수 없는 대화가 있으면 그 기록 전체를 거부할지, 되돌릴 수 있는 것만 할지 정해 보고한다. 권장: **전체 거부**하고 어느 대화가 막는지 보여 준다(부분 되돌리기는 V1 밖).
- journal 상태(예: Undoing, Undone) 추가 시
  - incomplete 판정과 IncompleteApplyRecoveryService: Undone은 종료 상태, Undoing은 미완료
  - 크래시 후 복구는 되돌리기 Snapshot 기준
- 같은 기록을 두 번 되돌릴 수 없다. 최신이 아닌 기록도 전제 조건이 맞으면 허용한다. 이 판단을 보고한다.

### 9_4-05 Snapshot 정리(SnapshotRetentionService)
- 기록 화면에서 선택 삭제를 할 수 있고, "30일 이상 지났고 되돌리기 불가인 기록 정리"를 제공한다.

- 삭제 금지
  - 진행 중이거나 미완료 상태(Prepared/Applying/Undoing)
  - 다른 Home의 Snapshot

- 삭제는 Snapshot 루트 안의 해당 디렉터리만 지운다. 경로 검증(루트 밖, 링크·정션 거부)을 한다.

### 9_4-06 Codex 흔적 검사(읽기 전용)
- 대상 thread가 다음에 나타나면 "Codex에서 이미 열어 본 대화라 되돌릴 수 없습니다"로 거부한다.
  - (a) `thread_history_*.sqlite`의 `thread_id` 컬럼을 가진 테이블(실측: thread_turns, thread_items, thread_history_projection_state)
  - (b) global-state `electron-persisted-atom-state` 안의 thread id 문자열
  - (c) `session_index.jsonl`의 그 thread id 줄(실측에서는 생기지 않았지만 보수적으로 확인)
- thread_history 스키마는 실제 C:\Users\User\.codex에서 **읽기 전용**으로 확인해 보고한다.
- 파일이 없으면 흔적 없음이다. 파일은 있는데 스키마를 알 수 없으면 보수적으로 거부한다.

## 4. 안전 규칙 (이 단계에서 특히 중요)
- **실제 C:\Users\User\.codex에는 절대 쓰지 않는다.** 되돌리기를 실제 데이터에 실행하지 않는다.
  - 스키마 확인은 읽기 전용으로만 한다. 작업 전후 4개 파일 SHA-256을 비교해 보고한다(state_5.sqlite, session_index.jsonl, .codex-global-state.json, config.toml).
  - 사용자가 Codex를 쓰는 중이면 값이 바뀔 수 있다. 그때는 열지 않았다는 사실과 수정 시각만 보고한다.
- **실제 %LOCALAPPDATA%\CodexBackupManager\Snapshots의 기존 Snapshot을 지우거나 바꾸지 않는다.** 실제 가져오기 기록이 들어 있다. 테스트는 temp Snapshot 루트를 쓴다.
  - 앱을 띄워 기록 화면을 본다면 [삭제]·[정리]·[되돌리기]는 누르지 않는다.
  - 기록 목록을 실제 폴더로 읽어 보는 것(읽기 전용)은 괜찮다. 그 결과(개수·종류·되돌리기 가능 여부 분포)를 보고한다.
- 되돌리기는 §2.2 순서를 빠짐없이 따른다. Snapshot 없이는 아무것도 지우지 않는다. Snapshot 사본 전체를 live에 덮어쓰는 방식으로 되돌리지 않는다.
- 확인하지 않은 컬럼·키를 쓰지 않는다(CLAUDE.md §33). global-state는 9_5a 게이트와 직렬화기 규칙을 그대로 따른다.
- 복제본을 CODEX_HOME으로 codex.exe 실행 금지. 로그에 원문·경로·제목·ID 금지.
- 사용자가 실험 빌드(artifacts\test-*)나 개발 빌드 앱을 실행 중일 수 있다.
  - 그 프로세스를 종료하지 않는다. artifacts 폴더는 건드리지 않는다.
  - 빌드가 잠기면 저장소를 bin/obj/.git 없이 스크래치로 복사해 빌드·테스트하고 그렇게 보고한다.
- TDD: 안전 거부 경로(흔적, fingerprint 불일치, 프로젝트 남기기, Rollback)는 RED를 먼저 보거나 임시 변형으로 RED를 확인한다. 변형 확인 뒤에는 파일 시각을 갱신해 다시 빌드한다(9_3-1에서 있었던 일).
- 빌드 경고 0 · 오류 0. 불확실하면 추측하지 말고 보고서 7번에 질문으로 남긴다.
