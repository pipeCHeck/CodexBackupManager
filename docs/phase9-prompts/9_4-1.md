## 2. 이번 범위

### 9_1-17 간헐 실패 테스트

  원인은 자식 프로세스가 아직 쓰고 있는 ready 파일을 File.ReadAllText로 읽다가 난 sharing violation이다.
- 읽기에 성공하고 기대 내용이 확인될 때까지 조건 대기(상한 있음, 실패 시 경과 시간 메시지)로 고친다. 필요하면 자식 쪽 ready 파일 쓰기도 temp+move로 원자적으로 만든다.
- 제품 코드는 바꾸지 않는다. 가능하면 전체 동시 실행을 여러 번 반복해 확인하고 횟수를 보고한다.

### 9_4-01 Apply 직후 기록(journal 확장)
- 성공한 Apply가 끝날 때(Completed 기록 시점) 그 Apply가 쓴 대상의 fingerprint를 기록한다.
  - 새 rollout 파일: 경로, 길이, SHA-256
  - 이어 붙인 rollout: 경로, 이전 길이/해시(Snapshot 기준), 이후 길이/해시
  - INSERT한 threads 행: thread id + 행 fingerprint(되돌리기 시 비교할 컬럼들의 값 해시. 어떤 컬럼을 넣는지 정하고 보고한다. Codex가 대화를 열면 바뀌는 컬럼(updated_at 등)은 포함해야 한다)
  - UPDATE한 threads 컬럼: thread id + 컬럼별 이후 값 fingerprint(이전 값은 Snapshot DB 사본에서 읽는다)
- Summary: 백업 파일 이름, 적용 시각, 새로 가져옴/이어받음 개수, 대상 thread ID 목록. **대화 제목·경로 원문은 넣지 않는다.** 화면은 현재 카탈로그에서 제목을 찾는다.
- 기존 journal 호환은 반드시 지킨다.
  - 새 필드는 선택 필드로 추가한다.
  - Phase 8의 journal 구조 검증(TryReadDetailed의 SnapshotId/CodexHomePath/State/UpdatedAtUtc 검사)을 약하게 만들지 않는다.
  - 새 필드가 없는 옛 journal은 "되돌리기 불가"로 읽혀야 한다.
- 원자적 쓰기(temp+flush+move) 패턴은 기존 journal과 같게 한다.

### 9_4-02 가져오기 기록 화면

  - 표시 항목: 날짜·시각, 백업 이름, 결과, 개수, 되돌리기 가능 여부와 사유
  - 이 PC에는 개발 중 테스트가 남긴 Snapshot이 이미 300개 이상 있다(대부분 다른 temp Home). 다른 Home의 기록은 목록에 넣지 않는다.
- 항목을 고르면 대상 대화 목록(현재 카탈로그의 제목)과 [되돌리기] 버튼이 보인다.
- 기록 목록을 만드는 동안 Codex Home과 Snapshot 폴더에 쓰기 0건이다.

### 9_4-03 되돌리기(ImportUndoService, Restore 계층)
- 순서는 CLAUDE.md §2.2의 쓰기 순서를 따른다.
  1. RestoreProcessLock 획득
  2. Codex 실행 확인(시작 시 + 첫 쓰기 직전 이중 확인, 기존 가드와 같은 방식)
  3. 대상 기록이 같은 Home이고 fingerprint가 있는지 확인
  4. **전제 조건 확인**: 현재 파일·행이 fingerprint와 같고 Codex 흔적이 없는지(9_4-06). 하나라도 다르면 쓰기 0건으로 거부하고 사유를 준다.
  5. 되돌리기 전용 **새 Snapshot** 생성(되돌리기가 바꿀 파일 전부)
  6. journal에 되돌리기 진행 상태 기록
  7. 역연산
     - 새로 만든 rollout 파일 삭제
     - 이어 붙인 rollout을 이전 길이로 자르기. 앞부분 해시가 이전 해시와 같을 때만. 자르기도 temp+atomic replace
     - INSERT한 threads 행 DELETE
     - UPDATE한 컬럼을 Snapshot DB 사본의 이전 값으로 복원
     - DB 작업은 한 트랜잭션
  8. 사후 검증: 대상 파일·행이 가져오기 직전 상태와 같은지, 다른 대화는 그대로인지
  9. journal에 되돌림 완료(Undone) 기록
- 도중 실패나 취소 → 되돌리기 Snapshot으로 Rollback한다. 결과는 "되돌리기를 취소하고 원래대로 두었습니다"다.
- journal 상태를 추가하면(예: Undoing, Undone) 두 경로가 새 상태를 올바르게 다뤄야 한다.
  - incomplete-apply 판정과 IncompleteApplyRecoveryService: Undone은 종료 상태, Undoing은 미완료
  - 크래시 후 복구: 되돌리기 Snapshot으로 원상복구
- 같은 기록을 두 번 되돌릴 수 없다. Undone이면 버튼을 비활성화한다.
- 최신 기록이 아닌 것을 되돌릴 때도 fingerprint가 맞으면 허용한다. 그 대화가 이후 가져오기로 다시 바뀌었다면 fingerprint가 달라 자연히 거부된다. 이 판단이 맞는지 보고한다.

## 4. 안전 규칙 (이 단계에서 특히 중요)

- **실제 C:\Users\User\.codex에는 절대 쓰지 않는다.** 되돌리기를 실제 데이터에 실행하지 않는다.
  - 9_4-06 스키마 확인만 읽기 전용으로 하고, 작업 전후 4개 파일 SHA-256을 비교해 보고한다(state_5.sqlite, session_index.jsonl, .codex-global-state.json, config.toml).
- **실제 %LOCALAPPDATA%\CodexBackupManager\Snapshots의 기존 Snapshot을 지우거나 바꾸지 않는다.** 테스트는 temp Snapshot 루트를 쓴다. 앱을 띄워 기록 화면을 본다면 [삭제]·[정리]·[되돌리기]는 누르지 않는다.
- 되돌리기는 CLAUDE.md §2.2 순서(검사 → Codex 실행 확인 → 검증 → Snapshot → 적용 → 검증 → 실패 시 Rollback)를 빠짐없이 따른다. Snapshot 없이는 아무것도 지우지 않는다.
- DB 사본(Snapshot) 전체를 live DB에 덮어쓰는 방식으로 되돌리지 않는다. 그 Apply가 쓴 것만 역연산한다.
- 복제본을 CODEX_HOME으로 codex.exe 실행 금지, 로그에 원문·경로·제목 금지
- TDD: 결함(9_1-17)과 안전 거부 경로는 RED를 볼 수 있으면 보고한다. 빌드 경고 0 · 오류 0, 전체 테스트 통과. 불확실하면 추측하지 말고 보고서 7번에 질문으로 남긴다.
