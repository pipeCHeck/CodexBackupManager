## 1. 배경 (관리 대화방이 실측으로 확인한 사실)

- 9_0-B 실험: 이 앱이 만든 DB 프로젝트 2개는 DB 기준으로 정상이다. 행·루트·키가 있고 대화 project_id도 연결돼 있다.
  Desktop도 대화에 마우스를 올리면 프로젝트 이름을 보여 준다. 그러나 **사이드바 프로젝트 목록에는 나타나지 않는다.**
- Desktop 사이드바 프로젝트 목록은 `.codex-global-state.json`의 **레거시 저장소**에서 온다.
  - `local-projects`: 객체. 레거시 ID → `{"id","name","rootPaths":[...],"createdAt","updatedAt"}`. 시각은 ms 정수, 필드는 이 5개뿐이다.
  - `project-order`: 레거시 ID 문자열 배열. 지금 키 집합이 `local-projects`와 같다.
  - `app-server-project-id-by-legacy-project-id-by-host`: `{"local:<CODEX_HOME 경로>": {레거시 ID: DB 프로젝트 ID}}`. 지금 host 키는 1개다.
  - `app-server-projects-migration-by-host[host]`: `projectsMigrated=true`, `threadAssignmentsMigrated=false`
- Desktop이 직접 만든 프로젝트 46개는 모두 두 저장소에 함께 있다.
  - 최근 레거시 ID는 UUIDv4(소문자 하이픈)이고, 오래된 것은 `local-` + SHA-256(루트)의 앞 32자다.
  - DB `project_idempotency_keys.key`가 그 레거시 ID다(53/53).
  - `project-order`의 순서 번호가 DB `projects.position`과 46/46 같다.
  - 지운 프로젝트 7개는 매핑과 키만 남는다.
- Desktop을 실행해도 새 DB 프로젝트를 레거시 쪽에 자동으로 추가하지 않았다.
- `thread-project-assignments`는 필요 없다. 9_0-A에서 DB `project_id`만으로 대화 소속이 반영됐다. 이번에도 쓰지 않는다.
- 파일 형식: UTF-8(BOM 없음), 줄바꿈 없는 한 줄 compact JSON(JS `JSON.stringify` 형식), 비ASCII 문자는 그대로 쓴다.
  Python `json.dumps(ensure_ascii=False, separators=(',',':'))`로 바이트까지 같게 다시 만들 수 있었다(354,817바이트, `\u` 이스케이프 12개, `\/` 원문 5곳).
  키 순서는 파일에 나온 순서 그대로다.
- 이 PC에는 이미 이 앱이 만든 프로젝트 2개가 레거시 항목 없이 있다(DB position 46·47, 키 접두사 `codex-backup-manager:import:v1:`).

## 2. 이번 범위

### 9_5a-01 GlobalStateProjectGate (읽기 전용 판정, Codex 층)
다음이 모두 맞을 때만 "레거시 기록 가능"이다.
- 파일이 있고, UTF-8(BOM 없음) JSON 객체로 파싱된다.
- **왕복 바이트 동일**: 9_5a-02 직렬화기로 손대지 않은 문서를 다시 쓰면 원래 바이트와 정확히 같다.
- `local-projects`가 객체이고, 모든 값이 위 5필드 객체이며, `id`가 키와 같다.
- `project-order`가 문자열 배열이다.
- 매핑 객체에 현재 Codex Home과 맞는 host 키(`HostKeyMatches`)가 **정확히 1개** 있다. 그 host의 `projectsMigrated == true`다.
결과는 카탈로그 `ProjectDirectory.ProjectCreation`에 반영한다.
- 이 게이트가 실패하면 새 프로젝트 생성 자체를 포기한다. 사이드바에 안 보이는 프로젝트를 만들지 않는다.
- 결과는 CreationUnsupported(기타 대화로 가져오기 + 기존 A안 안내)다. 실패 사유 enum을 보고한다.
- 실제 C:\Users\User\.codex\.codex-global-state.json에 대해 이 게이트를 **읽기 전용**으로 돌린 결과(통과 여부, 왕복 동일 여부)를 보고한다.

### 9_5a-02 GlobalStateWriter (순수 변환 + 원자적 쓰기)
- 직렬화기: JS `JSON.stringify`와 같은 compact 형식으로 쓴다.
  - 문자열은 `"`, `\`, 제어 문자만 이스케이프한다(`\b \f \n \r \t`, 그 밖은 `\u00xx` 소문자). 짝이 없는 서로게이트는 `\udxxx` 소문자로 쓴다. 그 외 문자(한글, `/` 등)는 그대로 쓴다.
  - 숫자는 원문 토큰을 그대로 옮긴다(재포맷 금지). 새로 넣는 숫자는 정수다.
  - 키 순서는 보존하고, 새 키는 끝에 붙인다.
  - 손대지 않은 값은 원래 표현을 그대로 유지한다(예: 원문 JSON 조각 재사용). 구현 방식을 보고한다.
- 변환(순수 함수): 입력은 원본 바이트 + 추가할 프로젝트 목록 (DB ID, 이름, 루트 표시 경로, 생성 ms)이다.
  1. `local-projects`에 `{ "id": L, "name": 이름, "rootPaths": [루트], "createdAt": ms, "updatedAt": ms }` 추가. L은 새 UUIDv4(`Guid.NewGuid()` 소문자 "D")
  2. `project-order` **끝**에 L 추가(사이드바 맨 아래. DB position = MAX+1과 맞는다)
  3. 매핑 host 객체에 `L: DB ID` 추가
  - 다른 키와 값은 바꾸지 않는다. `thread-project-assignments`, `electron-saved-workspace-roots`, `pinned-project-ids` 등은 쓰지 않는다.
  - 같은 DB ID가 이미 매핑에 있으면 추가하지 않는다(멱등).
- 쓰기: 같은 폴더에 temp 파일을 만들어 flush한 뒤 원자적으로 교체한다. 기존 `cbm-restore-tmp` 정리 규칙과 같은 이름 규칙을 쓴다.

### 9_5a-03 RestoreExecutor 통합
- 새 프로젝트를 만드는 Plan이면 Snapshot 대상에 global-state 파일을 넣는다.
- 쓰기 순서(Codex 실행 확인을 첫 쓰기 직전에 다시 한 번):
  1. 기존 DB 트랜잭션(프로젝트 + 대화) 커밋
  2. global-state 쓰기(같은 nowMs)
  3. 사후 검증
  4. 실패하면 Snapshot으로 DB와 global-state를 함께 Rollback
- Planner와 트랜잭션 안에서 9_5a-01 게이트를 다시 확인한다(계획 뒤 파일이 바뀌면 거부).
  global-state의 해시를 계획 시점 값과 비교해, 바뀌었으면 NotReady로 처리하는 방식도 검토해 보고한다.
- 사후 검증
  - 다시 읽은 파일이 파싱되고 게이트를 통과한다.
  - 수정한 세 키를 뺀 모든 최상위 키가 원본과 의미상 같다(가능하면 바이트 조각도).
  - 세 키에는 추가분 외 변경이 없다.
  - 새 항목·순서 끝·매핑이 정확하다.
  - fresh catalog의 ProjectDirectory에서 그 프로젝트가 DB ID와 레거시 ID로 합쳐져 보인다.
- fault injection 지점을 추가한다: global-state temp 쓰기 중, 교체 직후, 검증 전. CrashSim도 1건 추가한다(global-state 교체 직후 강제 종료 → 다음 실행 때 복구).
- 결과 화면 문구는 그대로 둔다. 다만 이제 사이드바에도 보인다는 전제와 어긋나는 문구(예: ⓘ "사이드바 반영은 확인 중")가 남아 있으면 지운다.

### 9_5a-04 보정: 사이드바에 안 보이는 이 앱 프로젝트
- 감지(읽기 전용): DB 프로젝트 중 idempotency key가 `codex-backup-manager:import:v1:`로 시작하는데 레거시 매핑에 없는 것
- 메인 화면에 한 줄 안내를 띄운다: "이 앱으로 만든 프로젝트 N개가 Codex 사이드바에 보이지 않습니다. [사이드바에 표시]"(감지 0개면 숨김)
- 실행 파이프라인은 RestoreExecutor와 **같은 구성요소**를 쓴다. 새 메커니즘을 만들지 않는다.
  1. Codex 실행 확인(시작 + 쓰기 직전)
  2. 프로세스 락
  3. fresh 재감지
  4. Journal + Snapshot(global-state)
  5. 쓰기(9_5a-02)
  6. 검증
  7. 실패 시 Rollback
  8. IncompleteApplyRecovery가 이 작업의 미완료 Journal도 복구한다
- 순서: DB position 오름차순으로 `project-order` 끝에 붙인다. 이름·루트는 DB 값이고, 시각은 DB `created_at_ms`다.
- DB는 바꾸지 않는다. 확인 대화상자를 띄우고, 결과를 표시한다(N개 추가 / 실패 사유). 다시 실행하면 감지 0개(멱등)다.
- Codex 실행 중이면 시작하지 않고 안내한다(정책 B와 같은 문구 체계).

## 4. 안전 규칙
- **실제 C:\Users\User\.codex에는 절대 쓰지 않는다.** 게이트 확인과 감지는 읽기 전용으로만 한다.
  작업 전후 4개 파일 SHA-256을 비교해 보고한다(state_5.sqlite, session_index.jsonl, .codex-global-state.json, config.toml).
  사용자가 Codex를 쓰는 중이면 값이 바뀔 수 있다. 그때는 열지 않았다는 사실과 수정 시각만 보고한다.
- 앱을 띄워 보더라도 [가져오기]·[새 폴더 만들기]·[사이드바에 표시]는 누르지 않는다.
- global-state 쓰기는 RestoreExecutor/보정 파이프라인 안에서만 한다. 새 쓰기 경로를 만들지 않는다.
- 왕복 바이트가 같지 않거나 구조가 확인한 형태와 다르면 **쓰지 않는다**(CLAUDE.md §33). 추측으로 필드를 채우지 않는다.
- 로그에 경로·프로젝트 이름·레거시 ID·DB ID를 남기지 않는다(개수와 결과 enum만).
- 복제본을 CODEX_HOME으로 codex.exe 실행 금지.
- 사용자가 실험 빌드(artifacts\test-9_0B)나 개발 빌드 앱을 실행 중일 수 있다.
  - 그 프로세스를 종료하지 않는다.
  - 빌드가 잠기면 저장소를 bin/obj/.git 없이 스크래치로 복사해 빌드·테스트하고 그렇게 보고한다.
- TDD: 안전 거부 경로(게이트 실패, 계획 후 변경, Rollback 후 바이트 원복)는 RED를 볼 수 있으면 보고한다. 빌드 경고 0 · 오류 0. 불확실하면 추측하지 말고 보고서 7번에 질문으로 남긴다.
