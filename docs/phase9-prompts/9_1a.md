### 1. 배경 (관리 대화방이 실측으로 확인한 사실)

- 이 PC의 Codex는 대화↔프로젝트 연결을 두 가지 ID 체계로 가진다.
  - SQLite `state_5.sqlite`의 `projects(id)`/`project_roots`: DB 프로젝트 46개, 루트 53개. `threads.project_id`는
    `REFERENCES projects(id) ON DELETE SET NULL` 외래키다. 실측 416행 중 채워진 행은 0개다.
  - `.codex-global-state.json`
    - `local-projects`: **레거시 ID**의 프로젝트 46개
    - `thread-project-assignments`: thread → 레거시 ID, 72건
    - `app-server-project-id-by-legacy-project-id-by-host`: 레거시 ID → DB ID 매핑. 46개 전부 매핑됨
    - `app-server-projects-migration-by-host["local:<home>"].threadAssignmentsMigrated = false`
- 현재 카탈로그(`CodexCatalogBuilder`)는 `CodexProjectResolver`가 돌려준 **원시 ID**로 프로젝트 그룹을 만든다. 그래서 같은 폴더가
  레거시 ID 그룹과 DB ID 그룹으로 나뉘어 **중복 표시**된다(실측 2건, 결함 D).
  또 `CodexCatalog.Projects`는 **대화가 1개 이상인 프로젝트만** 담는다(결함 A의 원인).
- 개발 PC에서 Codex가 실행 중이면 테스트 7건이 실패한다(결함 I). `CrashRecoveryIntegrationTests` 5건과
  `MainViewModelApplyTests` 2건이 실제 프로세스 목록(`CodexProcessGuard.SystemRunningProcessLister`)을 보기 때문이다.
  제품 버그가 아니라 테스트가 호스트 환경에 의존하는 문제다.

### 2. 이번 범위 (이것만 한다)

**9_1-01 (결함 I) 테스트를 호스트의 Codex 실행 여부와 무관하게 만든다**
- `MainViewModelApplyTests`의 2건: `MainViewModel`이 쓰는 Restore 호출에 프로세스 목록 제공자를 주입할 수 있게 한다.
  기본값은 반드시 기존 `CodexProcessGuard.SystemRunningProcessLister`다.
- `CrashRecoveryIntegrationTests` 5건: 자식 프로세스 `CodexBackupManager.Restore.CrashSim`이 테스트 전용 경로로 "Codex 없음" 목록을 쓰게 한다.
- 제약
  - **배포되는 앱(`CodexBackupManager.App`)에 가드를 끄는 스위치(환경 변수, 명령줄 인자, 설정)를 만들지 않는다.**
    주입 경로는 internal + `InternalsVisibleTo`(테스트/CrashSim 전용) 수준으로 제한한다.
  - 실제 가드 동작은 기존 `CodexProcessGuardTests`가 계속 검증한다. 가드 로직은 바꾸지 않는다.
  - 격리 후에도 "Codex가 실행 중이면 적용이 막힌다"를 확인하는 테스트가 최소 1건은 남아 있어야 한다(가짜 `codex` 프로세스 목록 주입).
- 보고서에 네가 테스트를 돌릴 때 실제로 Codex가 실행 중이었는지 적는다(`Get-Process *codex*` 결과).

**9_1-02 레거시→DB 프로젝트 ID 매핑 읽기**
- `GlobalStateReader`(또는 그 `ProjectGraph`)에 `app-server-project-id-by-legacy-project-id-by-host`를 읽는 기능을 추가한다.
  형태: `{ "local:C:\\Users\\User\\.codex": { "<legacyId>": "<dbProjectId>", … } }`
- host key 선택: `local:` 뒤 경로를 현재 Codex Home과 **canonical 비교**(`CanonicalPath`)해서 고른다. 없거나 형식이 다르면
  빈 매핑이다(예외 없이, 경고만). 다른 host key의 매핑은 쓰지 않는다.
- 읽기 전용이다. 파일을 수정하지 않는다.

**9_1-03 Domain 타입 추가** (`src/CodexBackupManager.Domain/Codex/Projects/`)
- `KnownProjectRoot(DisplayPath, Canonical, ExistsOnDisk)`,
  `KnownProject(Key, DbProjectId?, LegacyProjectIds, DisplayName, Roots, ConversationCount)`,
  `ProjectDirectory`(목록 + 조회: canonical 루트 → `ProjectLookupResult{Found|Ambiguous|None}`, DB 또는 레거시 ID → KnownProject), `ProjectDirectory.Empty`
- `Key` 규칙: `DbProjectId ?? "legacy:" + 대표 레거시 ID`. 설계 §5.1과 이름이 달라지면 이유를 보고한다.

**9_1-04 `ProjectDirectoryBuilder`** (Codex 계층, 순수 함수에 가깝게)
- 입력: `ProjectTableReader` 결과(projects, project_roots), global-state `local-projects`, 9_1-02 매핑, 대화 수 집계
- 규칙(설계 §4.2)
  1. DB 프로젝트마다 KnownProject를 만든다.
  2. 레거시 프로젝트는 매핑이 가리키는 DB 프로젝트에 합친다(LegacyProjectIds에 추가, 루트 합집합).
  3. 매핑이 없는 레거시 프로젝트는 **canonical 루트가 같은 DB 프로젝트가 정확히 1개**일 때만 합친다. 아니면 레거시 전용 KnownProject(`DbProjectId=null`)다.
  4. 같은 canonical 루트가 서로 다른 KnownProject 2개 이상에 걸리면 `FindByRoot`는 `Ambiguous`다.
  5. 루트 실존은 `Directory.Exists`로만 판정한다(읽기 전용).

**9_1-05 카탈로그에 `ProjectDirectory` 노출 + 트리 그룹 중복 제거(결함 D)**
- `CodexCatalog`에 `ProjectDirectory`를 추가한다(`init` 속성, 기존 생성자와 호출부 유지, 기본 `ProjectDirectory.Empty`).
- `BuildProjectGroups`의 그룹 키를 원시 ID가 아니라 **KnownProject.Key**로 정규화한다. 레거시 ID로 배정된 대화와
  DB ID/cwd 폴백으로 배정된 대화가 같은 프로젝트면 한 그룹이 된다.
- `CodexProjectResolver`의 authority 규칙(`threadAssignmentsMigrated`에 따른 우선순위)은 **바꾸지 않는다.** 결과 ID를 정규화하는 단계만 추가한다.
- `ConversationEntry.Project`(원시 배정 결과)는 그대로 둔다. 정규화된 키가 필요하면 별도 속성으로 추가한다.
- **영향 점검(필수, 보고서에 결과 기재)**: 그룹 ID(`ProjectEntry.ProjectId`)가 바뀌면 다음이 영향을 받는다. 각각 확인한다.
  - (a) Export manifest의 `projects[].projectId` 값: Backup Format V1 자체(필드·형식)는 바꾸지 않는다. 값이 어느 ID가 되는지 적는다.
  - (b) `ProjectPathMapper`/Import Preview
  - (c) `MetadataDifferenceAnalyzer.ProjectAssignmentDiffers`
  - (d) App 트리와 선택 상태
  - (e) `RestoreValidator`의 project_id 검사
  - (f) 기존 테스트 기대값

  기존 테스트의 기대값을 바꿔야 한다면 **왜 바뀌는 게 맞는지** 보고서에 근거를 쓴다. 근거 없이 기대값만 맞추지 않는다.

**테스트**
- **9_1-T1** ProjectDirectory: DB 전용 / 레거시 전용 / 매핑으로 합침 / 매핑 없이 루트로 합침 / 같은 루트 DB 2개 → Ambiguous /
  루트 실존 판정 / 다른 host key 매핑 무시 / 매핑 JSON 형식 이상 → 빈 매핑
- **9_1-T2** (결함 D, **RED를 먼저 실제로 확인**) 레거시 ID로 배정된 대화와 cwd 폴백(또는 DB ID)으로 배정된 대화가 같은 폴더면 카탈로그에서 한 그룹
- **9_1-T7(부분)** 전체 테스트 GREEN. 9_1-01 이후에는 Codex가 실행 중이어도 GREEN이어야 한다(가능하면 실제로 Codex를 켠 상태로 한 번 돌려 확인하고, 못 했으면 못 했다고 적는다).
- 테스트 fixture는 **합성으로만** 만든다. 필요한 테이블(`projects`, `project_roots`, FK 포함)과 global-state JSON은 테스트 코드에서 temp로 생성한다.
  공유 fixture(`tests/Fixtures/CodexHome`)를 고쳐야 한다면 최소한으로 하고 이유를 보고한다. **실제 사용자 데이터를 fixture로 복사하지 않는다.**

### 4. 공통 규칙

- **원본 보호**: 실제 `C:\Users\User\.codex`에는 절대 쓰지 않는다. 실제 데이터로 확인하고 싶으면 읽기 전용으로만 하고, 작업 전후에
  `state_5.sqlite`, `session_index.jsonl`, `.codex-global-state.json`, `config.toml`의 SHA-256을 비교해 보고한다.
- **복제본 주의**: `.codex` 복제본을 `CODEX_HOME`으로 지정해 Codex 바이너리(`codex.exe`)를 실행하지 않는다.
  복제본 DB의 `rollout_path`가 원본 절대경로를 가리켜 원본이 오염된다(실제 발생 사례 있음).
- **TDD**: 결함 수정은 RED를 실제로 본 뒤 GREEN으로 만든다. 보고서에 RED를 실제로 봤는지 항목별로 적는다.
- **frozen contract**: `ImportPreview`/`ImportPlan`/`RevisionRelation`의 기존 필드 의미는 바꾸지 않는다(이번 범위에서는 건드릴 일이 없어야 한다).
- **로그 redaction**: 경로·제목·원문을 로그에 남기지 않는다(`Redact` 규칙 유지).
- **빌드 기준**: `dotnet build CodexBackupManager.sln -c Release` 경고 0 · 오류 0, `dotnet test CodexBackupManager.sln -c Release` 전체 통과.
- 불확실한 것은 추측으로 구현하지 않는다. 공식 소스, 실측, 최소 재현 순서로 확인하고, 그래도 모르면 보고서 7번에 질문으로 남긴다.
