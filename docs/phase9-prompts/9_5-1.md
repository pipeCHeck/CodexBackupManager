## 1. 배경 (관리 대화방이 사용자와 함께 확인한 사실)

- **9_0-A 실험 결과 (a).**
  - 이 앱이 실제 사용자 .codex에서 가져온 대화의 `threads.project_id`를 등록 프로젝트의 DB ID로 기록했다.
  - Codex Desktop 사이드바가 그 대화를 그 프로젝트 아래에 보여줬다.
  - global-state(`thread-project-assignments`)에는 쓰지 않았다. 이 PC는 `threadAssignmentsMigrated=false`인데도 DB 연결이 반영됐다.
  - 따라서 이번 단계도 **DB만 쓴다**. global-state 쓰기(9_5a)는 취소됐다.
- 아직 모르는 것이 하나 있다. **새로 만든 DB 전용 프로젝트**(global-state `local-projects`/`project-order`에 없음)도 Desktop 사이드바에 보이는가?
  이것은 9_5 빌드로 사용자가 실험 9_0-B에서 확인한다. 추측으로 global-state를 건드리지 않는다.
- Desktop은 켜질 때 가져온 행의 `updated_at_ms`를 갱신하고 `cwd`를 `\\?\` 형식으로 정규화한다. `project_id`는 유지한다. 이번 단계에는 영향이 없다.
- 공식 코어의 프로젝트 생성 순서(`create_project`)는 한 트랜잭션(BEGIN IMMEDIATE) 안에서 이렇게 진행한다.
  1. idempotency key 조회 → 있으면 그 프로젝트 재사용
  2. `id = UUIDv7`, `position = MAX(position)+1`(없으면 0)
  3. `INSERT projects(id, name, metadata JSON '{}', position, created_at_ms, updated_at_ms)`
  4. `project_roots`에 루트를 position 순서로 INSERT
  5. `UPDATE threads SET project_id`
  6. `INSERT project_idempotency_keys(key, project_id, created_at_ms)`
- 검증 규칙
  - validate_name: 앞뒤 공백 제거 후 비어 있으면 거부
  - validate_idempotency_key: 비어 있으면 거부, 512바이트 이하
  - validate_roots: 절대 경로, 논리·canonical 중복 거부, `path.display()` 형식으로 저장(`\\?\` 없음)
- 지금 가져오기 화면은 미등록 폴더를 A안으로 처리한다(기타 대화 + "Codex에서 폴더를 한 번 연 뒤 새로고침" 안내).
  ProjectTargetKind.CreateNew는 enum만 있고 쓰이지 않는다. ProjectTargetDecision.NewProjectName은 지금 "적용 불가 사유"로 처리된다.

### 9_5-02 쓰기(StateDatabaseWriter.CreateProject)
- 기존 Apply의 **같은 SQLite 트랜잭션** 안에서 thread INSERT보다 먼저, 공식 순서대로 쓴다.
  1. project_idempotency_keys에서 key 조회
     - 있으면 그 project_id를 재사용한다. 그 프로젝트 행과 루트가 실제로 있고 canonical 루트가 같은지 확인하고, 아니면 실패 → Rollback
  2. 트랜잭션 안에서 루트 충돌 재확인: project_roots 전체를 읽어 canonical 비교. 같은 루트가 이미 있으면 실패 → Rollback(중복 생성 금지)
  3. `INSERT INTO projects (id, name, metadata, position, created_at_ms, updated_at_ms)`
     - metadata='{}', position=`COALESCE(MAX(position), -1) + 1`, created=updated=now ms
  4. `INSERT INTO project_roots (project_id, position, path)`, position 0
  5. thread INSERT(기존 InsertThread, project_id=새 id, cwd=RootPathDisplay)
  6. `INSERT INTO project_idempotency_keys (key, project_id, created_at_ms)`
- global-state(.codex-global-state.json)에는 **쓰지 않는다.**
- Snapshot 대상은 이미 state DB(+WAL/SHM)를 포함한다. 새 파일은 생기지 않는다. 실패하면 기존 Rollback이 프로젝트 행까지 되돌리는지 확인한다.

### 9_5-03 스키마 게이트(SchemaCompatibilityChecker)
- 실측 스키마와 정확히 같을 때만 생성을 허용한다.
  - projects(id TEXT PK, name TEXT NOT NULL, metadata TEXT NOT NULL, position INTEGER NOT NULL, created_at_ms INTEGER NOT NULL, updated_at_ms INTEGER NOT NULL)
  - project_roots(project_id FK→projects ON DELETE CASCADE, position, path, PK(project_id, position))
  - project_idempotency_keys(key, project_id, created_at_ms)
  - threads.project_id FK→projects(id)
- 컬럼·NOT NULL·PK·FK를 PRAGMA로 확인한다.
- 불일치 → 생성만 포기한다. Preview/Plan의 해당 목적지는 Uncategorized/CreationUnsupported다. Apply는 나머지를 계속한다.
- 실제 C:\Users\User\.codex에서 이 스키마를 **읽기 전용**으로 다시 확인하고 보고한다(PRAGMA table_info / foreign_key_list / index_list).

## 4. 안전 규칙 (이 단계에서 특히 중요)

- **실제 C:\Users\User\.codex에는 절대 쓰지 않는다.** 스키마 확인은 SQLite Mode=ReadOnly로만 하고, 작업 전후 4개 파일 SHA-256을 비교해 보고한다
  (state_5.sqlite, session_index.jsonl, .codex-global-state.json, config.toml). 앱을 띄워 보더라도 [가져오기]는 누르지 않는다.
- 프로젝트 생성은 기존 RestoreExecutor 파이프라인 안에서만 한다. 순서: Codex 실행 확인 → fresh preflight → Operation Plan → Snapshot → 쓰기 → 사후 검증 → 실패 시 Rollback. 새 쓰기 경로를 따로 만들지 않는다.
- 공식 SQL 순서와 제약을 그대로 따른다. 확인하지 않은 컬럼이나 값을 추측해서 쓰지 않는다(CLAUDE.md §33). 스키마 게이트를 통과할 때만 쓴다.
- 중복 프로젝트를 만들지 않는다: fresh 재판정 + 트랜잭션 안 루트 재확인 + idempotency key
- 복제본을 CODEX_HOME으로 codex.exe 실행 금지, 로그에 원문·경로·제목 금지(프로젝트 이름도 로그에 남기지 않는다)
- TDD: 안전 거부 경로와 결함(9_1-17)은 RED를 볼 수 있으면 보고한다. 빌드 경고 0 · 오류 0, 전체 테스트 통과. 불확실하면 추측하지 말고 보고서 7번에 질문으로 남긴다.
