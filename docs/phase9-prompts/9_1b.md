## 1. 배경 (관리 대화방 점검 결과)

9_1a 점검 결과는 통과다. 새로 만든 ProjectDirectory로 이 PC에 등록된 프로젝트 전체(대화 0개 포함, 레거시 ID 병합)를 알 수 있게 됐다.
그런데 Import 쪽은 아직 이것을 쓰지 않는다. 관리 대화방이 실제 .codex 복제본으로 재현한 현재 동작은 다음과 같다(PC A에서 X 프로젝트 대화 3개 Export → PC B에 가져오기).

| Case | 상황 | 현재 결과 | 9_1b 이후 기대 |
|---|---|---|---|
| 0 | 원본 경로가 PC B에 실존하고, PC B Codex에 등록된 프로젝트지만 대화는 0개 | NotFound, project_id=null, cwd 원본 | 자동 연결: project_id = 그 DB 프로젝트 ID, cwd = 루트 |
| 1 | 사용자가 Codex에 등록되지 않은 새 폴더를 지정 | 화면은 "사용자가 지정함", 실제로는 project_id=null, cwd 원본 | 동작은 같다(A안: 기타 대화). **화면이 "기타 대화로 들어갑니다"라고 정확히 말해야 함** |
| 2 | 대화가 있는 등록 프로젝트 폴더로 지정 | 정상 연결 | 그대로 |
| 3 | 등록됐지만 대화 0개인 프로젝트 폴더로 지정 | 무시됨(결함 A) | 연결됨 |
| 4 | 레거시 ID로 배정된 대화가 있는 프로젝트 폴더로 지정 | 9_1a 이전 RolledBack(FK 위반) → 9_1a 부수 효과로 Succeeded | 그대로 + 레거시 전용 프로젝트(DB ID 없음)도 FK 위반 없이 처리 |

원인
- ProjectPathMapper.Resolve와 RestoreOperationPlanner.ResolveLocalProjectId가 CodexCatalog.Projects(대화 있는 그룹)만 본다.
- 폴더 실존(Directory.Exists)을 판단에 쓰지 않는다.
- 연결할 ID가 실존 projects.id인지 보장하지 않는다. threads.project_id는 REFERENCES projects(id) 외래키다.

확정된 원칙(설계 §4.4)
- 프로젝트 ID는 PC마다 다르다. 대상 PC에서의 연결은 항상 "루트 경로 → 대상 PC의 ProjectDirectory"로만 판정한다.
  백업 manifest의 projectId나 대화의 resolvedProjectId를 연결 판정에 쓰지 않는다.
- threads.project_id에는 ProjectDirectory의 KnownProject.DbProjectId만 쓴다. DbProjectId가 없는(레거시 전용) 프로젝트로는 연결하지 않는다.
- 9_1a 이전에 만든 백업은 manifest 프로젝트 ID가 레거시 ID일 수 있다. 루트 기준 판정이라 그대로 동작해야 한다.

## 2. 이번 범위 (이것만 한다)

### 9_1-06 ProjectTarget + ProjectTargetResolver (Backup)
- Domain(또는 Backup)에 ProjectTargetKind{Uncategorized, LinkExisting, CreateNew}, ProjectTargetReason, ProjectTarget(Kind, Reason, FolderPath, LinkDbProjectId, NewProjectName)을 추가한다.
  enum 값 목록은 설계 §5.2를 따른다. 9_1b에서는 CreateNew를 만들지 않는다. 미등록/레거시 전용은 Uncategorized + 해당 Reason이다.
- ProjectTargetResolver.Resolve(백업 프로젝트 원본 루트들, 사용자 지정 폴더?, ProjectDirectory) 판정 순서(설계 §6 9_1 의사코드)
  1. 폴더 = 사용자 지정 폴더, 없으면 원본 루트 중 이 PC에 실존(Directory.Exists)하는 첫 번째
  2. 폴더가 없음 → Uncategorized / OriginalRootMissing
  3. FindByRoot(canonical(폴더))
     - Found & DbProjectId 있음 → LinkExisting(DbProjectId) / OriginalRootRegistered 또는 UserSelectedRegistered
     - Found & 레거시 전용 → Uncategorized / LegacyOnlyProject
     - Ambiguous → Uncategorized / AmbiguousRoot(9_2 전까지 자동 연결 안 함)
     - None → Uncategorized / OriginalRootExistsUnregistered 또는 UserSelectedUnregistered
  4. 백업의 "기타 대화" 그룹 → NotApplicable(9_5 전)
- 순수 로직으로 만든다. 파일 I/O는 Directory.Exists뿐이다.

### 9_1-07 ImportPreview에 판정 결과 채우기
- ImportProjectPreview.SuggestedTarget(ProjectTarget)을 추가한다(init 속성, 기존 생성자 유지). Build와 ApplyManualProjectPathOverride 둘 다 채운다.
- ImportConversationPreview에 LocalLocation, IsCompressedRollout, RequiredAncestorThreadIds를 추가한다(init 속성).
  - LocalLocation(ExistsLocally, KnownProjectKey, ProjectDisplayName, Archived): 로컬 카탈로그에서 그 대화가 속한 그룹. 없으면 "기타 대화".
    키는 ProjectDirectory.FindById(원시 ID)?.Key로 정규화한다.
  - IsCompressedRollout: 백업 체인에 .jsonl.zst 파일이 있는지
  - RequiredAncestorThreadIds: 백업 체인에서 선택 대화의 분기 조상 thread ID 목록
- ProjectPathMapping 호환 규칙. ProjectPathMapping은 Phase 6 frozen이다. **Status의 기존 의미를 바꾸지 않는다.**
  - 자동 판정: LinkExisting이면 AutoLinked(ResolvedLocalPath = 연결 루트), 그 밖에는 NotFound
    (Ambiguous, 레거시 전용, 미등록, 원본 없음 모두 NotFound)
  - 수동 재지정: 지금처럼 ManuallyLinked(= "사용자가 폴더를 직접 골랐다")를 유지한다. 실제 연결 여부는 SuggestedTarget이 말한다.
  - 기존 테스트가 이 의미에 의존한다(ImportPreviewBuilderTests의 수동 재지정 테스트 등).
    기대값을 바꿔야 하면 결함을 고정하고 있던 기대값인지 근거를 보고한다.

### 9_1-08 (결함 C) Planner가 실존 DB 프로젝트 ID만 쓰게 한다
- ImportPlanProject에 ResolvedTarget(ProjectTarget)을 추가한다(init 속성, 원래 9_2-03 항목의 일부를 앞당김).
  ImportPlanBuilder는 SuggestedTarget을 그대로 freeze한다. TargetProjectPath는 호환용으로 계속 채운다.
- RestoreOperationPlanner.ResolveLocalProjectId를 fresh catalog의 ProjectDirectory.FindByRoot 기반으로 교체한다.
  Found이고 DbProjectId가 있을 때만 그 ID를 반환한다. 레거시 전용/Ambiguous/None이면 null이다.
- Plan에 freeze된 목적지와 fresh 판정이 다르면 Operation Plan 생성을 거부한다. 기존 거부 경로를 쓰고, 사유는 "미리보기 이후 이 PC의 프로젝트 구성이 바뀌었습니다"다.
  비교 대상: Kind, LinkDbProjectId.
  예: 계획은 LinkExisting(X)인데 지금 X가 없음. 계획은 Uncategorized인데 지금은 등록 프로젝트가 있음.
- cwd remap 규칙(07_02)은 그대로다. project가 해석됐을 때만 cwd를 대상 루트로 바꾼다.
- RestoreValidator의 project_id 사후 검증이 새 규칙과 맞는지 확인한다.

### 9_1-09 Preflight
- ImportPlanPreflightValidator: ResolvedTarget이 LinkExisting이면 fresh ProjectDirectory에 그 DbProjectId가 있는지, 폴더가 실존하는지 확인한다.
  없으면 LocalStateChanged 또는 TargetPathUnavailable 중 기존 의미에 맞는 쪽을 쓰고 선택 이유를 보고한다.
- ResolvedTarget이 없는 Plan(9_1a 이전 방식으로 만든 Plan)도 기존 판정 그대로 동작해야 한다.

### 9_1-10 임시 UI 문구 (ImportPreviewViewModel만, 새 화면은 만들지 않음)
- 프로젝트 행 경로 문구를 SuggestedTarget.Reason 기준으로 바꾼다(설계 §9 메시지 표 참조). 예:
  - LinkExisting: "이 PC의 '○○' 프로젝트에 연결됩니다"
  - UserSelectedUnregistered: "Codex에 등록되지 않은 폴더입니다. 지금은 기타 대화로 들어갑니다. Codex에서 이 폴더를 한 번 연 뒤 [새로고침]하면 연결됩니다"
  - OriginalRootMissing: "원본 폴더가 이 PC에 없습니다. 폴더를 지정하지 않으면 기타 대화로 들어갑니다"
  - AmbiguousRoot: "이 폴더가 Codex에 여러 프로젝트로 등록되어 있어 자동으로 연결하지 않습니다"

- 대화 행의 "프로젝트 연결 다름"(MetadataDifferences.ProjectAssignmentDiffers, PC 간 원시 ID 비교)은 오해를 부른다. 이 대화에는 표시하지 않는다.
  대신 LocalLocation을 써서 "이 PC 위치: 기타 대화" / "이 PC 위치: ○○ 프로젝트"를 보여준다.

## 4. 공통 규칙

- 원본 보호: 실제 C:\Users\User\.codex에는 절대 쓰지 않는다.
  읽기 전용으로 확인했다면 작업 전후 state_5.sqlite, session_index.jsonl, .codex-global-state.json, config.toml의 SHA-256을 비교해 보고한다.
- 복제본 주의: .codex 복제본을 CODEX_HOME으로 지정해 codex.exe를 실행하지 않는다(복제본 rollout_path가 원본을 가리킨다).
- TDD: 결함 수정(T3, T5)은 RED를 실제로 본 뒤 GREEN으로 만든다. 새 기능 테스트는 RED를 못 봤으면 못 봤다고 적는다.
- frozen contract: ImportPreview/ImportPlan/ProjectPathMapping/RevisionRelation 기존 필드의 의미는 바꾸지 않는다. 추가만 한다(init 속성, 기존 생성자 유지).
- 쓰기 경로: Codex Home 쓰기는 RestoreExecutor 파이프라인(Snapshot → write → validate → Rollback) 안에서만 한다.
- 로그 redaction: 경로·제목·원문을 로그에 남기지 않는다.
- 빌드 기준: dotnet build CodexBackupManager.sln -c Release 경고 0 · 오류 0, dotnet test CodexBackupManager.sln -c Release 전체 통과.
- 불확실한 것은 추측으로 구현하지 않는다. 확인할 수 없으면 보고서 7번에 질문으로 남긴다.
